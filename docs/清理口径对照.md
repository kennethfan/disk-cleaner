## 1. 判定依据

"某条目录能不能清理"由三处各自决定，这是首次对照时多数不一致的根因。
修复后三处仍分工不变，但已通过 `MarkUncleanable` 串成一条链：

| 判断 | 代码位置 | 作用 |
| --- | --- | --- |
| 扫不扫、归哪类、什么风险 | `internal/scan/*.go` | 产出 `model.Item` 的 `Category` / `Risk` / `Permanent` |
| 允不允许删 | `internal/clean/engine.go` `DefaultRoots` + `internal/guard/guard.go` | 白名单根目录、精确禁止路径、前缀禁止、主目录保护 |
| 界面标不标"推荐" | `internal/webui/service.go` `catMeta` | 分类级 `safe` 标记，决定「推荐 / 需确认」与「全选推荐项」范围 |
| **扫描结果与可清理能力对齐** | `internal/controller/controller.go` `MarkUncleanable` | 扫描后按 guard 预筛，删不掉的标 `ReadOnly`（修复后新增） |

`MarkUncleanable` 在 `Controller.Scan()` 里调用，GUI 与 CLI 共用，因此两边看到的
可清理范围一致。这一条是修复的核心：此前扫描器只负责"发现了什么"，并不知道 guard
的白名单，导致界面把删不掉的路径也算进可回收空间。

`DefaultRoots` 只包含 `~/Library`、`~/Downloads`、`~/.Trash` 与若干 `~/.xxx` 缓存根；
`/Library`、`/private/var/log` 等系统路径不在白名单内；`~/Documents`、`~/Desktop`、
`~/Movies`、`~/Pictures`、`~/Music` 在 `homeProtectedSuffixes` 中被整体保护。

  `scan_test.go` `TestLargeFileScannerSkipsRedLineDirs`

## 5. P2：风险等级与归类（已修复）

| 路径 | 速查卡 | 修复前 | 修复后 | 代码位置 |
| --- | --- | --- | --- | --- |
| `~/Library/Developer/*`（DerivedData 等） | 🟡 黄 | 低（绿） | `RiskMedium` ✅ | `devcache.go:40` |
| `~/.m2/repository` | 🟢 绿 | 中（黄） | `RiskLow` ✅ | `devcache.go:55` |
| `/private/var/log`（asl） | 🟡 黄 | 低（绿） | `RiskMedium` ✅ | `caches.go:117` |
| `Docker` 虚拟机数据 | 🟡 黄 | 高（红） | `RiskMedium` + 只读 ✅ | `devcache.go:65/121` |
| `~/.cache/*` | A 用户级缓存 | 全归开发缓存 | 按目录名拆分 ✅ | `caches.go:79` |
| `~/Library/Logs` | E 系统缓存与日志 | 用户缓存 | 系统缓存 ✅ | `caches.go:118` |
| go-build / pip 父子重复 | B 独立条目 | 父目录整条覆盖 + pip 重复 | 已拆子目录、pip 仅 1 条 ✅ | `caches.go:40` |

**粒度与重复的修复细节**：

- `~/Library/Caches` 与 `~/.cache` 改为**按直接子目录拆分**（`caches.go:60` `cacheChildren`），
  不再产出父目录条目。实测本机 `~/Library/Caches` 拆出 **54 个子目录**、无父条目。
- pip 的重复靠 `devCacheRelPaths()`（`devcache.go:74`）解决：用户缓存扫描器拆分时
  跳过由开发缓存扫描器负责的子目录，同一目录只出现一次。测试验证 pip 只产出 1 条。
- `~/.cache` 归类按 `isDevCacheName()`（`devcache.go:110`）判断目录名前缀：
  `opencode`/`hyperframes`/`node`/`uv` → 开发缓存；`oh-my-opencode`/`gh`/`git` → 用户缓存。
  只收确定性高的工具名前缀，宁可漏判成应用缓存，也不把应用数据误标成可重建缓存。

## 6. 遗留问题

### 6.1 扫描结果被空目录淹没

真实扫描 **774 项中 478 项是 0 字节（62%）**，来源高度集中：

```
容器缓存 448 项，其中 440 项是 0 字节（98%）
```

macOS 给几乎每个系统组件都建了容器，绝大多数 `Data/Library/Caches` 是空的。
有效项（≥1 KB）只有 263 个，用户要在一堆 0 B 条目里翻找真正能清的东西。

非容器来源的 0 字节项也有（`Application Support` 下各应用的 `Cache` 空目录、
`~/Library/Caches/CloudKit` 等），但数量少得多。

**这不是首次对照列出的问题**，是 2026-11-04 复核时新发现的，已开 issue 跟踪：
[#1 扫描结果被空目录淹没](https://github.com/kennethfan/disk-cleaner/issues/1)。

### 6.2 速查卡表头数字过时 ✅

速查卡表头原写「已用 186 GB / 可用 25 GB（89%）」，2026-11-04 实测为
**总计 250.8 GB / 已用 204.0 GB / 可用 20.1 GB（81%）**。

已在同一次复核中更新速查卡：表头换成实测值、补上 `df` 与 Finder 两个可用空间
口径的对照、补 APFS 快照一行、修正 A/B 类归属与各项实测数字，并把 Docker 稀疏
文件「表观 64 GB / 实占 2.9 GB」的区别写进明细表。

## 7. 复现方式

```bash
# 扫描结果与 guard 判定可以直接对照
./bin/disk-cleaner scan --json | jq '.items[] | {category, path, read_only, size}'

# 安全边界测试
go test ./internal/guard/ ./internal/scan/ ./internal/controller/

# 统计空目录噪声占比
./bin/disk-cleaner scan --json \
  | jq '[.items[] | select(.size == 0)] | length'
```

对单条路径的放行判断，在 `internal/guard/guard_test.go` 里加用例，或在
`controller.Children` 的调试路径上观察 —— **不要用 `rm` 验证**。
