# 清理口径对照报告：扫描器 vs 速查卡

> 对照日期：2026-10-29 ｜ 代码基线：`a97a6c1` + 未提交的界面/卷名修复
> 对照对象：[macOS可清理目录速查卡.md](../macOS可清理目录速查卡.md)
> 本轮只出报告，**未改代码**。

## 1. 判定依据

"某条目录能不能清理"现在由三处各自决定，没有单一事实源，这是多数不一致的根因。

| 判断 | 代码位置 | 作用 |
| --- | --- | --- |
| 扫不扫、归哪类、什么风险 | `internal/scan/*.go`（`caches.go`、`devcache.go`、`junk.go`、`largefiles.go`、`snapshots.go`） | 产出 `model.Item` 的 `Category` / `Risk` / `Permanent` / `ReadOnly` |
| 允不允许删 | `internal/clean/engine.go:146` `DefaultRoots` + `internal/guard/guard.go:34/54/67` | 白名单根目录、精确禁止路径、前缀禁止、主目录保护 |
| 界面标不标"推荐" | `internal/webui/service.go:251` `catMeta` | 分类级的 `safe` 标记，决定「推荐 / 需确认」与「全选推荐项」范围 |

引擎行为：guard 拒绝的项不会中断整批，只标记 `Outcome.Skipped`（`internal/clean/engine.go:82`），
Web 界面把 `skipped || err` 显示成 ✕ 失败。

**关键事实**：`DefaultRoots` 只包含 `~/Library`、`~/Downloads`、`~/.Trash` 与若干 `~/.xxx` 缓存根，
`/Library`、`/private/var/log` 等系统路径**不在白名单内**；`~/Documents`、`~/Desktop`、`~/Movies`、
`~/Pictures`、`~/Music` 在 `homeProtectedSuffixes` 中被整体保护（`internal/guard/guard.go:67`）。

## 2. 结论摘要

| 级别 | 数量 | 含义 |
| --- | --- | --- |
| P0 安全口径冲突 | 3 | 界面能删，速查卡明确列为红线 / 不建议整删 |
| P1 显示与实际不符 | 2 | 标成「推荐」或可勾选，但引擎必然跳过 |
| P2 归类 / 风险 / 覆盖偏差 | 6 | 不影响安全，但和速查卡的说法对不上 |

## 3. P0：安全口径冲突

### P0-1 `Application Support/Google` 内的大文件可被清理

- 速查卡：🔴 永不触碰（Chrome 书签/密码/扩展，8.5 GB）。
- 代码：大文件扫描器把 `Library/Application Support` 整个递归进来（`internal/scan/largefiles.go:41`）；
  guard 的白名单含 `~/Library`，而 `Library/Application Support/Google` 不在任何保护清单里
  （`internal/guard/guard.go:34/54/67`），`Check` 会放行。
- 后果：Chrome 用户目录里超过 500 MB 的单个文件会作为「大文件」出现在列表里，可勾选移入废纸篓。
- 建议：把 `Library/Application Support/Google` 加入 `homeProtectedSuffixes`（guard 层面兜底），
  并让大文件扫描器跳过该路径（避免"列出来却清不掉"）。

### P0-2 iOS 设备备份作为垃圾文件可删

- 速查卡：🔴 红线清单「`Application Support/MobileSync` — iPhone 备份」。
- 代码：垃圾文件扫描器直接把 `Library/Application Support/MobileSync/Backup` 作为可清理项
  （`internal/scan/junk.go:45`，`RiskHigh` 但仍非只读）；guard 放行。
- 建议：从垃圾文件扫描器移除该项；若仍想展示，标 `ReadOnly` 并在 guard 中同步保护。

### P0-3 Docker 虚拟机目录整目录可删

- 速查卡：🟡 用 `docker system prune -a` 清镜像，不建议整目录动。
- 代码：开发缓存把 `Library/Containers/com.docker.docker/Data/vms` 作为可清理项
  （`internal/scan/devcache.go:61`，`RiskHigh`，note 已写明"删除即丢失"），guard 放行。
- 建议：按卡口径降级为只读提示，或从扫描列表移除并在 note 中给出 prune 命令。

## 4. P1：显示「推荐」但实际必然跳过

### P1-4 系统缓存类别

- 速查卡：`/Library/Caches`、`/private/var/log` 🟡，需 sudo、收益低。
- 代码：`internal/scan/caches.go:67-68` 把两者作为系统缓存项，`RiskLow`；
  界面上该分类 `safe=true`（`internal/webui/service.go:256`），属于「推荐」；
  但两条路径都不在 guard 白名单内 → 清理时 `Skipped`，界面显示 ✕。
- 建议：标 `ReadOnly`（只展示"系统里有这些缓存，需 sudo 自行处理"），并把分类改为不推荐。

### P1-5 用户文档区的大文件

- 速查卡：G 用户文档区"非缓存，只能人工判断"。
- 代码：大文件扫描器遍历 `Downloads`、`Documents`、`Desktop`、`Movies`、`Pictures`
  （`internal/scan/largefiles.go:36-40`）。其中 `Downloads` 在白名单内可清理；
  其余四个被 `homeProtectedSuffixes` 保护 → 列出但清理必失败。
- 建议：扫描后按 guard 预筛，把不可清理项标 `ReadOnly`（在 `controller.Scan` 里做，不用改 scan 包），
  或者干脆不扫受保护目录。

## 5. P2：风险等级与归类偏差

| 路径 | 速查卡 | 程序 | 证据 |
| --- | --- | --- | --- |
| `~/Library/Developer/*`（DerivedData 等） | 🟡 黄 | DerivedData 低（绿） | `devcache.go:39` |
| `~/.m2/repository` | 🟢 绿 | 中（黄） | `devcache.go:52` |
| `/private/var/log`（asl） | 🟡 黄（需 sudo） | 低（绿） | `caches.go:72` |
| `~/Library/Containers/com.docker.docker` | 🟡 黄 | 高（红） | `devcache.go:61`（另见 P0-3） |
| `~/.cache/*` | A 用户级缓存 | 开发缓存 | `devcache.go:58` |
| `~/Library/Logs` | E 系统缓存与日志 | 用户缓存 | `caches.go:35` |
| `~/Library/Caches/go-build`、`pip` | B 开发工具链（独立条目） | 被父目录 `~/Library/Caches` 整条覆盖；pip 又单列一次 | `caches.go:34`、`devcache.go:57` |

**粒度与重复**：速查卡按子目录看（Chrome 3.3 G、JetBrains 1.1 G、go-build 1.6 G），
程序只给整个 `~/Library/Caches` 一个条目，用户没法按子目录选择；同时 `~/Library/Caches/pip`
作为子项又单独出现，父子同时勾选会重复计入总大小（去重只按路径精确匹配，`scan.go` 的 `dedupeByPath`）。

## 6. 覆盖缺口

| 方向 | 内容 |
| --- | --- |
| 速查卡有、程序没有 | C 类容器内缓存（微信 `attach/video`、腾讯会议）、D 类 `Application Support/Slack` 的 `Cache`/`Code Cache` 子目录、微信开发者工具缓存 —— 卡里估算的约 26 GB"绿区"中这部分拿不到 |
| 程序有、速查卡没有 | APFS 快照（高风险、永久删除、界面只读） |
| 粒度 | `~/Library/Caches` 未拆子目录；`~/Library/Caches/pip` 父子重复 |
| 速查卡自身 | 表头「已用 186 GB / 可用 25 GB（89%）」是旧快照，今天实测为 250.8 GB / 已用 222.5 GB / 可用 28.3 GB；需要补 APFS 快照一行，并修正 go-build / pip 的归属 |

## 7. 建议的修复方案（未执行）

### 第 1 步：安全口径收敛（影响面小，建议优先）

1. `internal/guard/guard.go`：把 `Library/Application Support/Google`、`Library/Application Support/MobileSync`
   加入 `homeProtectedSuffixes`；把 `Library/Containers/com.docker.docker/Data/vms` 一并保护。
2. `internal/scan/junk.go`：移除 iOS 备份目标（或标 `ReadOnly`）。
3. `internal/scan/devcache.go`：Docker 目标改为 `ReadOnly` + note 指向 `docker system prune -a`。
4. `internal/scan/largefiles.go`：跳过上述红线路径。
5. 测试：`internal/guard/guard_test.go` 增加三条路径的拒绝用例；`internal/scan/junk_test.go`（如无则新增）
   断言不再产出 MobileSync。

### 第 2 步：显示口径与清理能力一致

1. `internal/controller/controller.go` 的 `Scan()` 返回前，用 `c.g` 对每个 item 做一次 `Check`，
   不可清理的标 `ReadOnly`（界面自动禁用复选框，与"指定目录扫描"一致）。
2. `internal/webui/service.go` 的 `catMeta`：系统缓存 `safe` 改为 `false`。
3. 测试：`internal/controller` 增加"guard 不允许的项被标只读"的用例。

### 第 3 步：归类与覆盖向速查卡靠拢

1. 拆分 `~/Library/Caches` 为子目录条目（至少 Chrome、JetBrains、go-build、pip），并去掉 pip 的父子重复。
2. `~/.cache` 按子目录拆分：命中开发者工具名的（opencode、zig、node、uv 等）归「开发缓存」，其余归「用户缓存」；`~/Library/Logs` 归「系统日志与诊断」。
3. 新增扫描器：`~/Library/Containers/*/Data/Library/Caches`（C 类）、
   `~/Library/Application Support/*/Cache*` 与 `Code Cache`（D 类）。
4. 风险等级按速查卡调整（Developer 系黄、Maven 绿、var/log 黄）。
5. 更新速查卡：补 APFS 快照、修正表头实测数字与 go-build/pip 归属。

**需要产品决策的两点**：是否允许工具删除 Chrome 用户数据 / iOS 备份 / Docker 整体（速查卡说不行，
但用户可能确实想删）；新增 C/D 类扫描会增加扫描时间与条目量，是否接受。

## 8. 复现方式

```bash
# 扫描结果与 guard 判定可以直接对照
./bin/disk-cleaner scan                     # 看各类别实际产出的条目
go test ./internal/guard/ ./internal/scan/  # 现有安全边界测试
```

对单条路径的放行判断，可在 `internal/guard/guard_test.go` 里加用例，或在 `controller.Children`
的调试路径上观察 —— 不要用 `rm` 验证。
